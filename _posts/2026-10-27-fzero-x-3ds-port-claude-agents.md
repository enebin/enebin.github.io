1998년 닌텐도 64로 나온 레이싱 게임 F-Zero X를 닌텐도 3DS로 옮겨 입체 3D로 돌려 보고 싶다고 해 보자. 실행 파일을 C 코드로 되돌려 놓은 디컴파일 소스는 이미 공개돼 있다. 그렇더라도 3DS의 그래픽 칩에 맞는 렌더러를 새로 짜고 세 코드베이스를 32비트 환경에 맞게 손본 뒤 오디오 드라이버를 옮기고 프레임 속도까지 끌어올려야 하니 사람이 직접 매달리면 몇천 시간은 걸리는 일이다.

[hypnotize.works](https://hypnotize.works/)에 공개된 회고는 이 작업을 다른 방식으로 끝낸 기록이다. 사람 한 명이 방향을 지시하고 프로젝트 내내 살아 있는 Claude 세션 하나가 작업을 조율하는 동안 하위 에이전트 147개가 코드를 짰다. 착수 24일 만에 New 3DS에서 F-Zero X가 입체 3D로 중앙값 59.6fps에 돌아갔고 이어진 43일 동안은 처음에 성능 문제로 포기했던 구형 Old 3DS까지 지원 범위에 넣었다.

정작 이 과정을 지휘한 사람은 처음부터 끝까지 코드를 한 줄도 읽지 않았다. 에이전트가 화면을 볼 수 없는 휴대용 게임기를 상대로 어떤 작업 규칙을 세웠고 하드웨어 병목을 어떻게 찾아냈으며 비용은 얼마나 들었는지 짚어 본다.

## 하나의 소스 트리에서 나온 세 가지 빌드

<figure>
  <img src="/assets/images/fzero-x-3ds-port-claude-agents-stack.svg" alt="디컴파일과 libultraship은 업스트림 그대로 두고 그 위에 패치 스택과 port/3ds를 얹은 구조">
  <figcaption>원본 두 저장소는 손대지 않고 3DS 고유 코드와 패치만 위에 얹었다.</figcaption>
</figure>

완성된 v1.0.0은 소스 트리 하나에서 세 종류의 콘솔 빌드를 만든다. 구형 Old 3DS용 기본 게임, 신형 New 3DS용 기본 게임, 그리고 코스 편집기와 머신 제작기가 들어 있는 확장팩인 64DD Expansion Kit까지 묶은 New 3DS용 빌드다. 모두 사용자가 자기 ROM에서 미리 추출해 SD 카드에 넣어 둔 에셋을 읽어 들이며 배포 파일에는 ROM이나 디스크 이미지가 들어 있지 않다. Grand Prix부터 Death Race까지 모든 모드가 돌아가고 음악은 3DS의 실제 소리 칩(DSP)을 거치며 입체 3D 깊이도 본체 슬라이더로 조절한다.

바탕이 된 오픈소스 저장소 두 곳은 직접 건드리지 않았다. F-Zero X 디컴파일인 `inspectredc/fzerox`와 N64 런타임 `libultraship`은 원본(업스트림)을 그대로 두고 그 위에 패치 스택만 얹었다. 3DS용 컴파일러인 `devkitARM`으로 빌드되도록 `newlib`를 13줄 고친 것이 외부 수정의 전부다. 3DS 고유 코드는 `port/3ds` 폴더에 모여 있고 1차 개발이 끝났을 때 15,039줄이었다. 2차 개발에서 추가된 네이티브 렌더러는 레이스 장면의 그리기 명령 목록(디스플레이 리스트)을 매 프레임 처음부터 순회하는 대신 게임 상태를 읽어 바로 GPU 명령을 찍어 내는 자체 인터프리터로, v1.0.0에서는 두 기종 모두 이 경로가 기본값이다.

## 에이전트는 3DS를 볼 수 없으니 사람이 SD 카드를 날랐다

<figure>
  <img src="/assets/images/fzero-x-3ds-port-claude-agents-loop.svg" alt="사용자, 지휘 세션, 워크트리별 에이전트, SD 카드, 3DS 실기를 도는 작업 순환">
  <figcaption>에이전트는 실기를 직접 볼 수 없어서 사람이 SD 카드로 날라 온 로그로만 결과를 확인했다.</figcaption>
</figure>

오래 살아 있는 Claude 세션 하나가 지휘자 역할을 맡아 프로젝트 메모리를 유지하고 작업 지시서(브리프)를 쓰고 브랜치를 합치며 사용자와 대화한다. 실제 코딩은 백그라운드 에이전트들이 나눠 맡는데 에이전트마다 독립된 작업 폴더인 git 워크트리 하나와 브랜치 하나, 커밋된 브리프 파일, 그리고 끝내기 전에 반드시 채워야 하는 진행 파일을 받는다. 하위 에이전트는 사용자와 직접 대화하거나 중심 브랜치(메인라인)를 건드리지 못하며 지휘자가 에뮬레이터로 1차 확인을 마친 뒤 위험한 변경은 실기 판정까지 통과해야 병합된다.

에이전트가 3DS 화면을 볼 수 없다 보니 사람이 눈과 손 노릇을 했다. 빌드를 SD 카드에 복사해 기기에 꽂고 달린 다음 기록된 로그를 들고 돌아오는 식이다. 1차 개발 기간에 사용자가 보낸 메시지 223개 가운데 "SD 카드 꽂았다"거나 "SD 카드 돌아왔다"는 말이 36번 나온다. 나머지 메시지도 입체 3D 60fps에 보탬이 되는 선택지만 추리라거나 지금 병렬로 돌릴 일이 더 있느냐는 식으로 방향과 증거와 판정에 집중됐다.

작업 규칙은 실패를 겪으며 하나씩 세워졌다. 조용히 끝난 오디오 에이전트의 변경분이 엉뚱한 바이너리에 섞여 들어간 사고를 겪은 뒤로는 **모든 최적화 레버에 당장 끌 수 있는 스위치를 달고 그 레버가 실제로 켜졌음을 증명하는 로그 한 줄을 반드시 찍게 했다.** 에이전트가 토큰 한도나 API 과부하로 중간에 멈추는 일도 잦아서 커밋 없이 죽은 에이전트 때문에 하루를 날린 뒤로는 진행 파일부터 쓰고 일찍 커밋하라는 규칙을 뒀다. 에이전트들이 서로의 에뮬레이터를 죽이고 SD 산출물을 덮어쓰던 사고는 잠금 파일로 차례를 기다리게 해서 막았다.

2차 개발에서는 Wi-Fi로 콘솔에 빌드를 바로 밀어 넣는 네트워크 링크, 새 렌더 경로가 기존 경로와 픽셀 단위로 같은지 대조하는 리플레이 장치, 병렬 브랜치를 합친 뒤 조합에서 생긴 손상만 찾아내는 상시 반대 검토가 더해졌다. 그때도 모든 병합은 사람이 최종 승인했다.

## New 3DS에서 60fps까지 다섯 라운드

1차 개발은 2026년 8월 11일부터 9월 3일까지 24일이 걸렸고 주간 사용 한도를 세 번 소진해 멈춘 날을 빼면 실제로 일한 날은 15일이다. 첫 나흘 동안 타당성 조사와 에이전트 팀 계획을 세우고 다섯 갈래로 기반 작업을 병렬로 돌린 끝에 부팅 버그 6개를 넘어 에뮬레이터에서 첫 레이스를 12~20fps로 띄웠다. 8월 21일 첫 실기 실행에서 48~50fps가 나왔고 9월 초에는 60fps 고정을 목표로 네 가지 최적화를 병렬로 밀었다.

| 라운드 | 중앙값 | 하위 10% | 60fps 도달 비율 |
| --- | --- | --- | --- |
| 캠페인 시작 | 51.3 | 39.2 | 9% |
| 브리지 메모이제이션 | 57.2 | 46.6 | 29% |
| HUD 아틀라스, 삼각형 메모, TMEM, 오디오 | 56.0 | 48.0 | 32% |
| 코어 2 렌더 스레드 | 57.6 | 44.6 | 14% |
| 선행 실행, 메인 스레드 브리지, 자동 LOD | 59.6 | 51.4 | 53% |

초반에는 이전 계산 결과를 재사용하는 메모이제이션과 화면 표시 요소(HUD)를 한 장의 이미지로 묶는 아틀라스 기법으로 속도를 올렸다. 그런데 렌더 스레드를 두 번째 CPU 코어로 분리한 라운드에서는 중앙값은 올랐지만 60fps 도달 비율이 오히려 14%로 떨어졌다. 이 문제를 다음 프레임을 미리 준비하는 선행 실행 모드 및 거리별 정밀도 조절(자동 LOD)과 결합해 풀어낸 끝에 전체 Grand Prix 실기 중앙값 59.6fps, 머신 30대가 몰린 구간의 하위 10% 51.4fps를 달성했다. 이 수치는 9월 3일 기준이며 이후 v1.0.0에서 따로 다시 재지는 않았다.

## Old 3DS의 발목을 잡은 16KB 명령어 캐시

<figure>
  <img src="/assets/images/fzero-x-3ds-port-claude-agents-icache.svg" alt="실기 프로브에서 핫 코드가 16KB일 때 CPI 1.06, 24KB일 때 4.10, 32KB일 때 5.62로 뛰는 그래프">
  <figcaption>핫 코드가 16KB 명령어 캐시를 넘는 순간 명령어 하나에 드는 사이클이 네 배로 뛴다.</figcaption>
</figure>

Old 3DS는 268MHz ARM11 코어 두 개에 L2 캐시가 없고 앱에 주어지는 메모리도 64MB뿐이라 첫 타당성 조사에서는 아예 제외됐던 기종이다. 2차 개발에서 다시 도전하면서 먼저 메모리 사용량부터 줄였다. N64의 RDRAM 영역을 절반으로 깎고 오디오를 스트리밍으로 바꾸고 텍스처 업로드에 상한을 뒀더니 기존 빌드가 부팅 중 죽던 실기에서 9월 29일 마침내 부팅에 성공해 약 10fps로 달렸다. 당시 프레임당 96ms 가운데 GPU가 바쁜 시간은 3.6ms뿐이었고 25.8ms는 게임 스레드가 오디오 잠금(뮤텍스)이 풀리기를 기다리는 시간이었는데 잠금 범위를 좁히자 0.2ms로 줄었다.

진짜 함정은 그다음에 나왔다. 에뮬레이터에서 크게 빨라진 보존 모드 렌더러를 실기에 올렸더니 프레임이 거의 움직이지 않았다. ARM11의 하드웨어 성능 카운터로 측정해 보니 렌더 경로는 명령어 하나에 평균 4.34사이클(CPI)이 걸렸고 전체 사이클의 43.6%가 명령어를 메모리에서 가져오느라 멈춰 있었다. 같은 반복문을 핵심 코드(핫 코드) 크기만 바꿔 돌린 실험에서는 16KB일 때 CPI 1.06이던 것이 24KB에서 4.10, 32KB에서 5.62로 치솟았다. PC 에뮬레이터는 Old 3DS의 16KB 명령어 캐시 한계를 흉내 내지 않으니 에뮬레이터에서 얻은 이득이 실기로 이어지지 않았던 것이다.

갈림길에서 먼저 검토한 안전한 길은 마지막 프레임을 시점만 바꿔 다시 제출해 초당 40장을 맞추는 포즈 재생이었는데 하늘이 떨리고 화면 가장자리가 찢어졌다. 사용자는 편법 대신 진짜 60fps로 가자고 결정했다. 10월 1일과 2일에 걸쳐 만든 네이티브 렌더러는 16KB 캐시에 맞춰 처음부터 다시 설계됐다. HUD, 트랙, 머신, 하늘, 효과, 그림자 같은 범주마다 작은 전용 루프 하나가 게임 상태 스냅샷을 돌며 GPU 명령어를 직접 쓰고 각 단계의 코드 크기를 16KB 안에 가뒀다. 그러자 범주별 CPU 합계가 21.1ms에서 9.1ms로 내려갔고 2D Grand Prix 중앙값 프레임 시간이 16.5ms에 들어왔다.

입체 3D는 왼쪽 눈 프레임을 한 번 만들고 그때 기록된 명령 스트림을 오른쪽 눈용으로 다시 제출하는 방식으로 풀어 10월 8일 내부 개발 카드 기준 Grand Prix 레이스 구간에서 59~60fps가 나왔다. 연산이 무거운 일부 코스는 안전장치가 걸려 30fps로 내려간다.

## 4,974달러와 사람 팀 35만 달러

<figure>
  <img src="/assets/images/fzero-x-3ds-port-claude-agents-cost.svg" alt="이 프로젝트의 24일과 4,974달러를 사람 팀 추정치인 약 6개월과 약 35만 달러 옆에 놓은 비교">
  <figcaption>같은 범위를 시니어 두 명과 QA가 맡았을 때의 중간 추정치와 나란히 놓으면 약 70배 싸고 7~8배 빠르다.</figcaption>
</figure>

1차 개발 동안 지휘 세션과 에이전트가 쓴 토큰은 모두 31억 7천만 개다. 물량의 96%는 이전에 읽은 문맥을 다시 불러오는 프롬프트 캐시 읽기였지만 비용에서 가장 큰 비중을 차지한 것은 모델이 새로 써낸 출력 토큰 1,320만 개였다. API 공개 정가와 1시간 캐시 쓰기 요율을 적용하면 4,974달러가 나온다. 다만 사용자는 정액 구독제를 썼기 때문에 해커뉴스 댓글에서 밝힌 실제 지출은 월 200달러 구독 3개월분인 600달러였다.

가장 비싼 수업료는 8월 14일에 나갔다. 사용량 한도가 끊긴 동안에도 900턴짜리 에이전트 두 개가 종료되지 않고 살아남아 큰 컨텍스트를 수백 번 다시 읽으면서 각각 210달러와 209달러를 태웠다. 맡은 브리프를 끝낸 에이전트는 즉시 멈춰야 한다는 교훈을 여기서 얻었다.

같은 범위를 시니어 엔지니어 두 명과 파트타임 QA가 맡았다면 5~8개월 동안 25만~45만 달러가 들었을 것으로 추산된다. 중간값과 견주면 약 70배 싸고 7~8배 빠르다. 물론 숙련된 팀이 붙었다면 남은 백로그까지 닫고 더 다듬어진 결과를 냈을 것이다. 그럼에도 이 비용 차이가 남긴 진짜 요점은 불확실한 아이디어 다섯 개를 동시에 시도해 보고 그중 세 개를 실기 측정 수치 위에서 미련 없이 접을 수 있을 만큼 시도가 싸졌다는 데 있다.

## 코드를 한 줄도 읽지 않은 사람이 남긴 말

회고 사이트 전체에서 사람이 직접 쓴 페이지는 하나뿐이고 나머지는 전부 작업을 수행한 에이전트가 작성했다. 그 한 페이지에서 지휘자는 자기 역할을 프로덕트 오너와 QA 테스터 사이 어딘가로 설명한다. Claude가 전략을 제안하면 승인하거나 되묻고 막히면 조사를 시키고 에뮬레이터 검증을 마친 빌드를 3DS에서 돌려 본 뒤 로그를 가져다주는 일을 3주 동안 되풀이했다.

> 나는 코드를 한 줄도 읽지 않았다. 진짜 기술적 결정을 내린 적도 없다.

2022년 ChatGPT를 처음 써 본 날부터 실존적 공포를 느꼈다는 이야기도 이어진다. 직접 손으로 짰다면 몇천 시간이 들었을 텐데 삶의 시간은 유한하니 자기만의 오리지널 게임을 만드는 일과 저울질하면 이 이식을 수작업으로 할 이유가 없었다는 것이다. 생성형 AI의 윤리는 여전히 흐릿하고 사회에 미칠 파장은 과소평가돼 있으며 이 프로젝트가 그 증거라는 문장으로 글은 끝난다.

흔히 다중 에이전트 코딩은 자동 테스트가 갖춰진 웹 앱에서 시연되곤 한다. 반면 이번 작업은 에이전트가 화면을 볼 수 없는 기기를 상대로 측정 주기가 SD 카드 왕복에 묶여 있었고 코드베이스는 저장소 셋에 패치 스택을 얹은 구조였다. 그 조건에서 147개 에이전트가 길을 잃지 않게 붙잡아 준 것은 모델의 영리함이 아니라 킬스위치와 한 줄짜리 증명 로그, 이른 커밋 같은 규칙, 그리고 실기 증거를 들고 와서 예와 아니오를 결정한 사람이었다.
