코딩 에이전트 열 개에게 각자 다른 작업을 맡겼다고 해 보자. 에이전트마다 자기만의 작업 폴더가 필요하다. 저장소가 작으면 문제가 없다. 그런데 저장소가 수십 GB라면 이야기가 달라진다. 에이전트가 일을 시작하기도 전에 코드를 받아 오느라 몇 분씩 기다린다.

에이전트가 코드를 잘 짤수록 이 대기 시간은 더 아프다. 코드 작성은 빨라졌는데, 코드를 받고 합치고 검사하는 길목이 그대로라서다. Anthropic은 이 문제를 가장 먼저, 가장 크게 겪은 회사다.

2026년 10월 13일, Anthropic은 엔지니어링 블로그에 [Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)을 올렸다. 모노레포(회사 전체 코드를 담은 하나의 저장소)를 Git에서 직접 만든 버전 관리 시스템 Scion으로 옮겼다는 내용이다. 이 글에서는 왜 Git으로는 안 됐는지, Scion은 무엇을 다르게 했는지 정리한다.

## 하루 2,500건이 3만 건이 됐다

<figure>
  <img src="/assets/images/anthropic-scion-source-control-scale.svg" alt="2026년 5월 하루 약 2,500건이던 머지가 9월 3만 건 이상으로 늘었고, CI 체크아웃 2,500만 번을 그대로 받으면 하루 600PB가 넘는다는 것을 보여주는 그림">
  <figcaption>머지 수가 열 배 넘게 늘자 저장소를 복사하는 비용이 감당할 수 없는 크기가 됐다.</figcaption>
</figure>

숫자부터 보자. 2026년 5월 Anthropic의 모노레포에는 하루 평균 약 2,500건의 변경이 머지됐다. 9월에는 하루 3만 건을 넘었다. 넉 달 만에 열 배 넘게 늘었다. Claude에게 맡기는 코드가 그만큼 늘었다는 뜻이다.

저장소 자체도 크다. main 브랜치 기록만 100GB 가까이 되고 압축한 작업 사본도 25GB가 넘는다. CI는 하루에 코드를 2,500만 번쯤 체크아웃한다. 개발자 환경과 에이전트 샌드박스, 연구 작업은 뺀 숫자다. 이걸 아무 요령 없이 받으면 하루 600PB가 넘는 Git 트래픽이 생긴다.

물론 그동안 손 놓고 있지는 않았다. 얕은 복제, 일부만 받는 체크아웃, 내부 미러 같은 우회책을 다 썼다. 한창때는 내부 Git 미러를 수백 대나 돌렸다. 하지만 머지 속도가 빨라질수록 미러를 운영하기가 더 어려워졌다. 미리 받아 둔 기본 사본은 금세 main과 멀어졌다. 일부만 받은 저장소에서는 diff나 blame(줄마다 누가 고쳤는지 찾는 기능) 같은 기본 기능을 계속 돌아가게 하기도 버거웠다. 원문은 이 상황을 한 문장으로 요약한다.

> As our merges per day grew more than tenfold, source control became our biggest development bottleneck.

## Git은 오프라인 세상을 위해 만들어졌다

<figure>
  <img src="/assets/images/anthropic-scion-source-control-model.svg" alt="Git은 모든 클라이언트가 저장소 전체 사본을 들고 오프라인에서 일하고, Scion은 서버가 기록과 커밋을 맡고 클라이언트는 필요한 파일만 받는 구조라는 비교 그림">
  <figcaption>Git은 누구나 전체 사본을 갖는 쪽, Scion은 서버가 무거운 일을 맡는 쪽으로 설계됐다.</figcaption>
</figure>

Anthropic이 찾은 근본 원인은 Git의 설계 전제였다. Git은 분산형이다. 모든 사용자가 저장소 전체를 복사해 두고 인터넷이 끊겨도 혼자 일할 수 있게 만들어졌다. 사람 개발자에게는 아주 좋은 성질이다.

그런데 Anthropic의 실제 사용 방식은 정반대였다. 클라이언트 대부분은 늘 온라인인 에이전트나 작업이었다. 이들은 저장소 전체가 필요 없다. 지금 고칠 파일 몇 개만 있으면 된다. **Git의 오프라인 우선 설계가 규모를 키우는 데 오히려 걸림돌이 됐다.**

그래서 팀은 Google의 Piper와 Meta의 Sapling을 참고해 원칙을 새로 세웠다. 클라이언트는 항상 온라인이라고 가정한다. 기록 조회, blame, 커밋, 머지, 리베이스는 모두 서버가 한다. 클라이언트는 필요한 파일만 받아 화면에 펼친다. 커밋이 서버에서 바로 만들어지니 push라는 단계도 없다.

작업 폴더도 선택 사항이 됐다. CI는 코드를 내려받지 않고 API로 변경 내용만 물어볼 수 있다. 자동 bisect(버그가 처음 생긴 커밋을 찾는 작업)나 자동 되돌리기도 로컬 저장소 없이 API로 돈다.

## Scion은 이렇게 움직인다

<figure>
  <img src="/assets/images/anthropic-scion-source-control-tiers.svg" alt="작업이 노드마다 있는 scion-daemon에 요청하고, daemon은 지역 scion-cache에, cache는 scion-server에, server는 Spanner와 클라우드 저장소에 묻는 4단 구조 그림">
  <figcaption>내용이 바뀌지 않는 데이터만 오가므로 층마다 캐시가 99% 넘게 맞는다.</figcaption>
</figure>

Scion의 기본 단위는 changeset이다. Git 커밋은 저장소 전체 트리를 가리키지만 changeset은 바로 앞 버전에서 바뀐 파일 목록만 담는다. 그래서 커밋 비용이 저장소 크기가 아니라 변경 크기에 비례한다. 쓰는 동안 잠금도, 서버끼리의 조율도 없다.

blame이나 파일별 기록 같은 정보는 changeset에 넣지 않는다. 원문은 이를 파생 데이터라고 부른다. 파생 데이터는 하나의 공통 방식으로 계산하는데, 미리 해 둘 수도 있고 요청이 올 때 할 수도 있다. 클라이언트는 이 내부 구조를 보지 않는다. 덕분에 서버 쪽 구조를 바꿔도 클라이언트를 업데이트할 필요가 없다. 복사 감지나 경로로 파일 찾기 같은 기능도 나중에 이렇게 덧붙였다.

코드를 받는 경로는 네 층이다. 각 작업은 같은 컴퓨터에 있는 scion-daemon에 묻는다. daemon은 지역별 scion-cache에, cache는 scion-server에 묻는다. 맨 아래에는 Spanner와 클라우드 저장소가 있다. 오가는 데이터는 내용 주소 방식이라 한번 만들어지면 바뀌지 않는다. 그래서 어느 층이든 마음 놓고 캐시할 수 있다.

결과는 이렇다. 층마다 캐시 적중률이 99%를 넘는다. 인프라 규모는 예전 Git 미러 인프라보다 200배 작아졌다. CI와 연구 작업의 체크아웃은 분 단위에서 초 단위로, 약 100배 빨라졌다. CI만 놓고 보면 CPU 여유가 25% 생겼다.

## 일곱 명이 다섯 달 만에 옮겼다

<figure>
  <img src="/assets/images/anthropic-scion-source-control-roles.svg" alt="Claude는 코드 작성과 재작성, 최적화, 충돌 수정을 맡고 엔지니어는 시스템 설계와 제약 지키기, 변경 의도 검토를 맡는다는 역할 분담 그림">
  <figcaption>코드는 Claude가 더 잘 쓰고, 사람은 무엇을 하지 말아야 할지 정한다.</figcaption>
</figure>

이 작업을 한 팀은 일곱 명이다. 이들이 Scion과 코드 리뷰 도구 Antique, 관련 시스템 여섯 개 남짓을 만들었다. 이전은 다섯 달 만에 끝냈다. 그 사이 하루 머지 수는 열 배로 늘었다.

엔지니어들은 코드 작성만큼은 Claude가 자신들보다 낫다고 평가했다. 대신 사람은 시스템 전체를 이해하고 설계의 득실을 따졌다. 원문은 엔지니어의 역할이 Claude에게 "안 돼"라고 말하는 것일 때가 많았다고 적었다. 예를 들어 Claude가 코드 리뷰 도구에 물으면 될 일을 커밋 기록 전체를 훑어서 해결하려 할 때다. 엔지니어는 이제 코드 한 줄 한 줄보다 변경의 의도를 검토한다.

Claude가 사람보다 나은 결과를 낸 장면도 있다. 사람이 손으로 만든 Git→Scion 데이터 이전 파이프라인을 Claude Mythos Preview에게 통째로 다시 짜라고 했다. 추가 지시 없이 나온 결과물은 메모리를 20배 덜 쓰고 4배 빨랐다. 순서와 자료구조의 불변 조건도 지켰다.

빨리 만들었다고 대충 만든 것은 아니다. 원문은 Scion을 회사에서 가장 많이 테스트된 코드베이스 중 하나로 꼽는다. 외부와 격리된 시뮬레이션과 퍼징(무작위 입력을 퍼부어 버그를 찾는 테스트)을 돌린다. 운영도 Claude가 거든다. 구성 요소마다 전담 Claude를 하나씩 붙여 로그와 지표를 지켜보게 한다. 보통의 알림이 놓치는 미묘한 이상을 이들이 잡아낸다.

일하는 방식도 바뀌었다. 전역 잠금을 거는 전통적인 머지 큐는 에이전트 규모에서 버티지 못했다. 그래서 머지 뒤와 배포 앞에 자동 테스트를 두는 쪽으로 옮겼다. 동시에 들어온 변경이 충돌할 수는 있다. 하지만 사람이 충돌을 알아채기도 전에 Claude가 대개 고쳐 놓는다.

## 정리: Git을 버리라는 이야기는 아니다

Anthropic은 Scion을 Git의 대체품으로 내놓지 않는다고 분명히 했다. Scion은 엔지니어가 수만 명이거나 에이전트가 아주 많이 코드를 쓰는 초대형 모노레포에서만 의미가 있다. Git과 동작 방식이 달라서 쓰려면 코드 리뷰, 검색, CI까지 다 바꿔야 한다. 내부 버전도 Anthropic에 맞춰 깊이 손댄 상태다.

그래도 남의 일로만 볼 수는 없다. Anthropic은 같은 문제가 앞으로 6~12개월 안에 다른 곳에도 퍼질 것으로 본다. 에이전트를 많이 쓰는 팀일수록 먼저 부딪힌다. 그래서 Git 사용자가 Git을 떠나지 않고도 쓸 수 있는 아이디어를 공유하겠다고 했다. 서버 쪽 API, 필요한 것만 주고받는 프로토콜 같은 것이다. GitHub, GitLab, 오픈소스 커뮤니티와 협력하겠다는 말도 덧붙였다.

이 글에서 가져갈 질문은 하나다. 우리 개발 인프라는 사람 몇십 명이 쓰는 속도에 맞춰져 있는가, 에이전트 수백 개가 쓰는 속도에 맞춰져 있는가. 지금 에이전트가 작업을 시작할 때 몇 분씩 기다린다면, 병목은 이미 모델이 아니라 그 앞의 길목에 있다.
